# 과제 11: 삽입 정렬과 쉘 정렬의 성능 비교

## 1. 실험 방법

- 데이터: `rand()`로 만든 무작위 정수입니다. `srand(2026)`으로 시드를 고정했으며, Visual Studio에서는 값이 0 ~ 32,767 범위로 나옵니다.
- 데이터 크기: n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 크기마다 원본 데이터를 한 번만 만들고, 세 정렬이 그 원본을 복사해서 사용했습니다.
- 비교 횟수: 데이터 값끼리 비교할 때마다 1씩 더했습니다. 반복문의 조건 검사, 데이터 생성, 복사는 세지 않았습니다.
- 확인: 정렬이 끝난 뒤 오름차순인지, `qsort()` 결과와 같은지 확인했으며 모두 맞았습니다.
- 간격(gap)
  - 기본: n/2, n/4, ..., 1 (n=1000이면 500, 250, 125, 62, 31, 15, 7, 3, 1)
  - Knuth: 1, 4, 13, 40, ... 중 n보다 작은 값을 큰 것부터 사용했습니다. (n=1000이면 364, 121, 40, 13, 4, 1)

## 3. 분석

**① 데이터 크기가 커지면 비교 횟수는 어떻게 변합니까?**
삽입 정렬은 n이 2배가 되면 비교 횟수가 약 4배가 되었습니다 (3.91 ~ 4.13배). 비교 횟수를 n²/4로 나누면 모든 크기에서 0.99 ~ 1.02가 나오므로, 삽입 정렬의 비교 횟수는 대략 n²/4번이라고 볼 수 있습니다. 새 원소를 넣을 때 앞쪽 원소의 절반 정도와 비교하기 때문입니다.
쉘 정렬은 n이 2배가 되어도 비교 횟수가 약 2.2 ~ 2.5배만 늘었습니다. 삽입 정렬보다 훨씬 천천히 늘어납니다.

**② 삽입 정렬과 쉘 정렬은 얼마나 차이가 납니까?**
n이 클수록 차이가 더 커졌습니다. n=1,000에서는 삽입 정렬이 쉘 정렬(기본)보다 약 17배 많이 비교했고, n=20,000에서는 약 159배 많이 비교했습니다. (Knuth와는 18배 → 178배)
삽입 정렬은 원소를 한 칸씩만 옮기므로, 작은 값이 뒤쪽에 있으면 앞까지 오는 데 비교를 아주 많이 해야 합니다. 쉘 정렬은 처음에 큰 간격으로 멀리 있는 원소끼리 비교하고 옮겨서 데이터를 대략 정렬해 둡니다. 그러면 마지막 간격 1 단계에서는 원소들이 이미 제자리 근처에 있어서 비교가 적게 듭니다.

**③ 기본 간격과 Knuth 간격은 얼마나 차이가 납니까?**
모든 크기에서 Knuth 간격이 더 적게 비교했습니다. 기본 간격이 Knuth보다 9% ~ 25% 더 많이 비교했습니다. 하지만 삽입 정렬과의 차이(수십 ~ 백 배)에 비하면 작은 차이이고, n이 커진다고 계속 커지지도 않았습니다. 크기마다 한 번씩만 측정했으므로 "Knuth가 10~20% 정도 더 적게 비교했다" 정도로만 말할 수 있습니다.

**④ 간격이 성능에 영향을 주는 이유는 무엇입니까?**
(이 부분은 일반적으로 알려진 설명이며, 이번 실험에서 직접 확인한 것은 ③의 결과입니다.)
기본 간격(n/2, n/4, ...)은 간격끼리 배수 관계이므로, 큰 간격에서 이미 비교한 원소들을 작은 간격에서 또 비교하게 됩니다. 그래서 데이터가 골고루 섞이지 않습니다.
Knuth 간격(1, 4, 13, 40, ...)은 서로 배수 관계가 아니므로 단계마다 새로운 원소끼리 비교하게 되고, 데이터가 더 골고루 정렬됩니다. 단계 수도 적습니다. (n=1,000일 때 Knuth 6단계, 기본 9단계) 이번 실험에서 Knuth가 더 적게 비교한 것도 이 설명과 일치합니다.

## 4. 결론

- 삽입 정렬은 약 n²/4번 비교하며, n이 2배가 되면 비교 횟수는 약 4배가 됩니다.
- 쉘 정렬은 n이 2배가 되어도 약 2.2 ~ 2.5배만 늘어납니다. n=20,000에서는 삽입 정렬보다 150배 이상 적게 비교했습니다.
- 간격은 Knuth 간격이 기본 간격보다 모든 크기에서 조금 더 좋았습니다.
